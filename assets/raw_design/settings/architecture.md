“已确认”指用户明确选择的决定；“目标要求”指原设计提出的需求；“待确认”指仍存在多种解释的方案。

## 2. 问题与目标

现有属性、标签、实体、区域、方格的职责重叠，编辑器控件风格和折叠层级不统一，脚本较为扁平，增加了人工与跨 agent 维护成本。

目标是建立明确的数据合同、模块职责与编辑器层级，迁移全部已实现功能。采用面向对象封装和组件组合，但不为了复杂度增加没有独立职责的继承层次。

## 3. 技术栈与职责

**已确认：继续 Three.js + JavaScript，Node.js 只管理 prefab。** 现有服务、资源校验及构建工具继续使用 Node.js，不因此迁移玩家状态机。

| 层 | 职责 |
| --- | --- |
| 资源定义 | entity/tag prefab 定义、校验、目录加载与程序写入；前端不得反向修改定义 |
| 游戏逻辑 | 实体行为、标签适用性、放置规则、机制与状态转换；不依赖编辑器 DOM |
| 编辑器 | 工具、选区、Inspector、图层、地图操作与历史；通过逻辑接口操作 |
| 渲染与输入适配 | Three.js 场景、拾取、相机、图标与 DOM；保持现有预览行为 |

**已确认：本文件的 MonoBehaviour 指浏览器中的 JavaScript 行为层，即可以被对象化和序列化的交互逻辑脚本。** 它与编辑器 UI 解耦，不是 Unity 组件，也不在 Node.js 执行游戏逻辑。

行为对象的序列化与恢复合同需要明确脚本身份、参数和状态如何对应，不能把方法或闭包直接当作 JSON 值。受控脚本引用与可序列化描述是建议方案，最终格式仍需确认；不得将“可序列化”误解为前端可以修改程序定义。

所有 player 状态机和玩家交互继续集中在 work/player.cjs。组件化不得把玩家选中、移动、折纸、朝向、区域推进、钥匙协调、动画、结束和历史重新分散到 UI 或其他实体脚本。

## 4. 概念与数据归属

### 4.1 方格

方格是整数坐标 (r,c) 对应的空间位置，负责坐标与占格关系。方格位置、实体实例、标签实例各有独立职责。颜色不决定机制。

地图维度、多格占格掩码和高度沿用现有规则。高度目前只影响渲染；重构不增加坡度通行、三维寻路或高度差移动限制。

### 4.2 实体与行为

实体是功能的主要载体，由 prefab 静态定义、地图实例及运行时状态组成；三者不可混为同一个可变对象。

实体可分静态与动态。纸张、钥匙、障碍和地图放置的 token 为现有实体；自动生成的 player 是唯一受控玩家。NPC 等仅是扩展方向。UI 不重新引入“地形”分类，现有 terrain 等兼容字段在迁移完成前仍保留。

目标要求：实体行为独立封装，并可由序列化描述恢复为行为对象。建议 prefab 引用受控脚本标识；脚本标识、序列化格式与文件命名在实现前确认，不根据任意输入路径加载脚本。

### 4.3 虚空实体

**已确认：虚空是完全透明的特殊实体，不可主动放置，可以选中和检视。** 它不因此成为可行走或正常传送目标，也不出现在主动放置列表中。

现状使用 tiles[r][c] === null；迁移须保留空格背景、虚空折线和不可通行语义。隐藏区域造成的视觉空白不能当作可编辑虚空，隐藏保护不可被绕过。

现有点击虚空清空选区与新增检视虚空的交互需要在 Q3 中确认，不能自行取消其中一种。

### 4.4 标签与区域

**已确认：所有标签均作为 prefab，序列化到 assets/prefab/tag。** 标签定义描述允许附着对象、属性和行为，标签实例记录实际附着对象及参数。标签支持静态标记、查询及触发功能，不是所有标签都有触发行为。

现有区域归属、折线、起点、入口、出口均需纳入目标标签系统。区域仍指具有同一 regionTag 的方格集合，不要求连通；同格多实体的区域冲突解析待确认。

折线是特殊标签，可附着允许它的实体，包括虚空；仍逐格放置、同方向连续合组、不同方向独立计算，不恢复无限直线或整线自动铺设。

### 4.5 BaseEntity 与建造

**已确认：实体 BaseEntity 定义允许放置在哪些实体上；标签 BaseEntity 定义允许附着在哪些实体上。** 它不是类继承关系。

**已确认：是否保留下层实体由对应实体行为封装具体实现。** 通用系统校验适用性并调用行为，不对所有实体统一硬编码替换或叠加。每个行为必须明确处理策略，缺失规则应报告错误。

放置合同应明确允许基底、受影响占格、保留/替换结果、标签处理、实例身份、撤销与失败原因。多格操作只处理实际占格；越界或隐藏保护失败整次拒绝，不能部分写入。

原文“一切基于纸张实体”不能解释为强制保留纸张底层；依赖由 BaseEntity 与行为表达。各现有 prefab 的允许基底需逐项确认，不得擅自收紧原有覆盖能力。叠层数据与交互见 Q4。

## 5. Prefab 与属性权限

目标目录：

```text
assets/prefab/
  entity/    # 所有实体定义
  tag/       # 所有标签定义
```

现状为 assets/prefab/*.json。迁移同步调整扫描、程序写入、校验、热刷新、预览目录、构建内嵌及独立导出；仅移动文件不算完成。

保留 ID、名称、可选颜色、尺寸、布尔占格掩码及实例快照语义。引用必须可解析，坏定义隔离报错，不使编辑器整体失效。前端不提供 prefab 创建/保存入口。

属性支持对象、列表及列表嵌套；类型、默认值、验证规则、权限是静态定义，实际值与临时调试状态分开。保留原来的三种修饰需求，统一拼写 serializable：

| 修饰 | 目标用途 |
| --- | --- |
| serializable | 是否参与程序管理的定义/状态序列化；不赋予前端保存修改的权限 |
| readable | Inspector 是否可显示 |
| tempEditable | 前端是否可临时调试 |

**已确认：前端只能临时调试，不能反向注射后端；地图实例修改不能保存。** 前端属性修改不得回写 entity/tag prefab、程序定义、行为代码或地图实例持久化数据。不自行增加第四种 editable 权限。

前端调试值必须与加载的定义及地图基线隔离。地图导出、localStorage 自动保存和独立游戏导出不得夹带临时修改；serializable=true 也不例外。颜色、钥匙名、区域及标签参数的前端修改不能沿用现有实现直接持久化，迁移时需要明确改变这部分行为。

用户已明确禁止地图实例修改保存；地图结构操作（放置、删除、复制粘贴、附着/移除标签）以及地图级名称/尺寸是否仍可保存，需要另行确认，不能自行视为例外，也不能推断整个地图保存功能已取消。

嵌套权限、默认值和父子冲突需要明确合同。UI 隐藏不等于授权；修改仍需类型、值域、BaseEntity 与隐藏保护校验。调试状态重置及历史规则见 Q6。

## 6. 编辑器与控件

编辑模式左侧分四个一级 Tab，右侧保留地图预览；ProBuilder、Inspector 是功能类比，不引入 Unity 插件。

| Tab | 内容 |
| --- | --- |
| 地图编辑 | 实体选择/放置、删除、选区、复制粘贴、折线逐格工具 |
| 检视 | 方格及实体身份、属性、临时调试、标签附着/移除和参数 |
| 地图属性 | 名称、描述、尺寸与已有地图级设置 |
| 图层 | 坐标、实体图标 checklist、折线、标签、区域显示 |

保留顶部中央名称显示/编辑及右侧 name / 编辑、name / 游玩编辑。不同面板引用同一名称状态；名称的持久化范围见 Q8。

统一控件：实体/标签用图标选择，显示过滤和出口钥匙用 checklist，布尔值用开关，枚举用单选，动作用按钮。留空规则依据数据约束明确。

父级折叠隐藏全部子级，子级记忆自身展开状态。切换 Tab 不重复绑定事件，不丢选区、不污染历史。不存在或不适用字段不渲染，例如无颜色属性隐藏颜色栏，只有出口标签显示目标区域与钥匙条件。

隐藏保护覆盖工具、Inspector、擦除、粘贴和批量入口。现有实体/区域已有保护；折线/标签总开关保护有缺口，需要完善，不能写为已完成。

游玩左侧方向旋转、折纸提示、任意传送等修改器保留原布局与规则。

## 7. 模块与事件

目标要求：实体/标签行为模块、查询校验服务、EventBus。广播用于通知，不替代命令校验，不得让监听器重复推进玩家动作。

事件合同明确名称、负载、发送时机、订阅生命周期与错误处理；模式切换、地图替换、面板销毁应清理订阅。操作先校验，再作为事务写入状态和历史，成功后通知，失败不留部分修改。

建议职责分组如下，具体路径在实施前固定并维护构建入口：

```text
work/
  player.cjs     # 玩家逻辑保留此入口
  core/          # 合同、事件、事务、通用校验
  entities/      # 实体行为与受控注册
  tags/          # 标签附着与行为
  editor/        # 工具、选区、检视、图层、历史
  ui/            # Tab、折叠、通用控件
  render/        # 原渲染接口适配
  resources/     # prefab 目录与写入
  tests/         # 模块与迁移回归
```

UI 框架尚未选定，组件化不以新增框架为前提；未确认前不改成 React/Vue。

可扩展模块随实现提供 README.md 与适用的 AGENTS.md，说明职责、数据类型、注册方法、扩展步骤、禁止事项、测试入口。沿用仓库 AGENTS.md 命名，不建立职责重复的 agent.md。
