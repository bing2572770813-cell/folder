# 触发机制需求：升降方块与易碎方块

状态：需求基线（未实现易碎方块）  
更新：2026-10-07

本文把升降方块和易碎方块放入统一的回合与实体事件合同，作为后续实现、测试和验收的清单。本文不能覆盖 `work/GAME_MECHANICS.md`、`docs/entity-transform-tree-product-design.md` 中已经确认的规则；发生冲突时先修正文档和实现的权威来源。

## 1. 目标

- 玩家成功行走和传送都能以明确的到达原因触发实体机制。
- 一次行动只使用一个 trigger，不因区域出口、传送或动画回调重复结算。
- 升降方块按回合推进，动画只展示已经结算的运行时高度。
- 易碎方块具备可验证的放置、运行、触发、显示、保存加载和撤销闭环。
- 编辑器预览、正式放置和游玩运行使用同一套实体约束。

本文 checklist 指验收待办清单，不表示编辑器已经提供了扳机选择控件。升降当前响应成功行动的回合结算；易碎的扳机配置属于待实现需求。

## 2. 术语和统一合同

### 2.1 到达原因

权威枚举位于 `work/player.cjs`：

```text
Trigger.Walk     = "walk"
Trigger.Teleport = "teleport"
```

一次实体事件只能携带一个到达原因。`enter`、`leave`、`interact` 是事件阶段，不是 trigger；初始化和原地交互可以没有到达原因。

### 2.2 回合生命周期

一次有效行动按以下顺序执行：

```text
validate -> snapshot -> leave -> action -> enter -> settle -> outcome -> present -> complete
```

- 无效行动、处理中再次输入、空闲帧和动画帧不推进回合。
- 逻辑结算失败必须恢复快照，不能保留部分组件、位置或运行时修改。
- 行走经过区域出口并传送到目标入口时，仍属于同一回合：出口使用 `walk`，目标入口使用 `teleport`，升降和其他一次性结算只推进一次。
- 渲染层读取结算后的状态，不负责推进回合、触发实体事件或决定破坏结果。

## 3. 升降方块需求

### 3.1 数据和放置

- 升降组件只能属于一个单格纸张实体；不能作为独立实体叠加。
- 同一方格最多一个纸张，因此最多一个升降控制来源。
- 组件数据是唯一权威来源：

```json
{
  "lift": {
    "minHeight": 0.09,
    "maxHeight": 1.4,
    "initialHeight": 0.09,
    "turnsPerLeg": 3
  }
}
```

- `turnsPerLeg` 范围为 1–100，默认 3。
- 旧 `durationMs` 只在兼容导入时转换为默认 3 回合，保存的新数据不得保留该字段。
- 放置预览和正式放置必须同时校验：单格纸张、升降组件归属、边界、隐藏格和现有叠加规则。

### 3.2 回合行为

- 无人占据时，方块在最低和最高高度之间往返。
- 每次成功 `walk` 或 `teleport` 行动结算一次升降段；一单程经过 `turnsPerLeg` 次有效行动到达另一端。
- 失败行动、转向、等待、选择、空闲帧和动画速度改变都不推进升降。
- 玩家占据方块时只允许下降；到达最低高度后保持。玩家离开后从当前高度继续往返。
- 升降不重复触发进入、离开、钥匙、火焰、冰冻、区域或其他地形效果。
- 撤销恢复玩家位置、回合状态、升降高度、方向和占据状态；重开恢复 `initialHeight`。

### 3.3 表现和保存

- 方块本体、升降贴图、边线、地形标记和相关选择高亮必须同步移动。
- 编辑模式显示 `initialHeight`；游玩模式显示运行时高度。
- 贴图不是实体、按钮、碰撞体或 trigger 来源。
- 运行时高度、方向和占据状态不得写回地图配置；保存加载后从配置重新建立运行时状态。

### 3.4 升降验收清单

- [ ] 单格纸张才能添加升降组件。
- [ ] 多纸张、独立升降实体、越界和隐藏格放置被原子拒绝。
- [ ] `walk` 成功推进一段，`teleport` 成功推进一段。
- [ ] 行走到区域出口再传送到入口只推进一次。
- [ ] 失败行动和空闲时间不推进。
- [ ] 玩家占据时只下降，最低处保持；离开后恢复往返。
- [ ] 动画速度不改变高度结算结果。
- [ ] 本体、贴图、边线和标记同步移动。
- [ ] 升降不重复触发其他机制。
- [ ] 撤销、重开和保存加载恢复正确状态。
- [ ] 编辑器和独立游戏浏览器验证无控制台错误。

## 4. 易碎方块需求

易碎方块目前尚未在实体目录、组件注册表或 `player.cjs` 中实现。本节是待确认后的最小需求，不得把未确认的破碎条件直接写入代码。

### 4.1 数据模型

建议使用实体组件表示易碎能力，不新增独立的旧式 `terrain` 事实字段。以下仅演示单枚举配置形状，字段名和默认值须在行为定稿后确定：

```json
{
  "fragile": {
    "trigger": "walk"
  }
}
```

要求：

- 单次实际 trigger 只能为 `walk` 或 `teleport`，不得存成数组或组合布尔值。
- 若提供扳机配置，编辑器采用单选枚举，并清楚显示当前值；机制验收清单与扳机选择控件分开。
- 首版是否提供耐久次数、触发阶段及破碎结果，按第 4.4 节定稿；未确认前不引入次数字段或计数规则。
- 破碎状态属于组件运行时，贴图和通行投影从该状态派生；除非产品明确要求持久化，否则不写回地图配置。
- 易碎能力属于实际实体节点；不能由颜色、贴图或 prefab 名称推断。
- 易碎方块是否必须有纸张承载，沿用实体叠加和 terrain 承载规则；不能通过易碎组件绕过承载校验。

### 4.2 触发和原子性

- 进入检查判断目标通行许可；不匹配破碎 trigger 不自动意味着禁止进入。进入许可与破碎效果分别定义。
- 拒绝行动不修改实体、不产生破碎效果、不推进回合；预览和 `checkEntry` 也不得执行效果。
- 破碎效果在已经确认的事件阶段执行；到达破碎还是离开破碎必须先定稿。
- 同一回合同一实体不重复应用一次性破碎效果，不因区域传送、重复渲染或动画完成回调重复执行。
- 如果后续机制导致本回合逻辑执行异常，恢复快照，包括玩家、回合和实体运行时。正常结算出的死亡属于回合结果，不能误当作执行异常回滚。
- `walk` 与 `teleport` 的行为必须分别测试；禁止以“有 trigger 但未区分原因”的布尔值替代枚举。

### 4.3 破碎表现

- 破碎由模拟层确定，渲染层只展示已确定的状态。
- 破碎后实体的碰撞、通行、地形承载、贴图、实体树、拾取和保存投影必须从同一权威状态重新派生。
- 破碎动画不能决定破碎时机，也不能在动画回调中再次推进回合。
- 若破碎导致玩家所在格失去承载，必须由回合结算统一处理掉落、失败或其他结果；本需求不新增隐含的物理规则。
- 编辑器必须能显示易碎配置和当前可编辑字段，但不显示伪造的运行时破碎状态为地图事实。

### 4.4 易碎方块待确认项

以下问题在实现前必须定稿：

- [ ] 破碎响应 `walk` 还是 `teleport`，是否允许设计者为实例选择枚举值，以及默认值是什么。
- [ ] 破碎阶段是到达 `enter`、离开 `leave`，还是回合结算 `settle`。
- [ ] 首版是一次触发即破碎，还是需要耐久次数。
- [ ] 破碎后的方块是变为虚空、变为不可通行残片，还是替换为指定实体。
- [ ] 破碎发生后玩家是否仍站在原格；若不再承载，采用哪一种已确认的掉落规则。
- [ ] 破碎状态是否只存在于本次游玩，还是允许保存到游玩存档。
- [ ] 易碎方块能否承载 terrain、钥匙或其他实体，以及破碎时这些上层实体如何处理。

### 4.5 易碎方块验收清单

- [ ] 未确认的破碎策略不会出现在编辑器可用选项中。
- [ ] 预览、正式放置和保存加载使用同一组件校验。
- [ ] `walk`、`teleport`、拒绝进入、重复事件分别有测试。
- [ ] 成功触发只结算一次，动画速度和帧率不影响结果。
- [ ] 进入拒绝无副作用；执行异常回滚实体、玩家和回合状态；正常失败结果只结算一次。
- [ ] 破碎后的实体树、贴图、碰撞、地形、拾取和保存投影一致。
- [ ] 撤销、重开、区域传送和折纸传送覆盖回归测试。
- [ ] 至少一个浏览器场景验证真实显示、交互和控制台错误。

## 5. 实现边界和验证入口

- `work/player.cjs`：玩家状态机、回合生命周期、trigger 传递、升降和易碎运行时结算。
- `work/backend/src/entities/components.ts`：`ArrivalTrigger` 类型、事件上下文和纯组件校验，与 `player.cjs` 的实际枚举合同保持一致。
- 实体组件/放置模块：组件归属、承载、叠加和原子放置校验。
- 渲染模块：读取运行时投影，负责本体、贴图和破碎表现，不推进规则。
- 推荐测试入口：`component-trigger.test.mjs`、`turn-manager.test.mjs`、`player-tree.test.mjs`、`work/test-player.mjs`。
- 最小闭环顺序：放置 → 编辑预览 → 行走/传送触发 → 回合结算 → 显示 → 保存加载 → 撤销/重开。

## 6. 完成标准

只有同时满足以下条件，才能将该机制标记为完成：

1. 触发枚举、事件阶段和回合顺序只有一个权威实现。
2. 失败行动没有部分状态修改，重复触发不会重复结算。
3. 升降方块的验收清单全部通过。
4. 易碎方块的待确认项已定稿，验收清单全部通过。
5. 自动测试、构建和浏览器验证结果已记录在对应提交中。
