# 开发规范

本文件规定 `work/` 下开发、修复、重构和优化的通用原则。修改前必须阅读本文件以及适用的 `AGENTS.md`，后续开发必须遵守。用户明确指示优先；项目的具体领域规则与模块约束以根目录和对应子目录的 `AGENTS.md` 为准。

具体优化路线、阶段任务和性能数据写入对应设计或优化文档，不作为本文件的长期规范。

## 开发执行流程

以下流程是每次修改的执行要求。只检查适用项；不适用的项目不需要补造机制、测试或文档。记录可放在已有任务说明、测试、提交说明或完成报告中，不要求另建检查清单文件。

### 修改前

- 阅读适用规范和相关实现，定位本次行为的权威数据、规则入口及消费者，再决定修改位置。
- 明确一个可验证的目标行为及失败边界。修 Bug 先复现；性能优化先记录场景和测量边界；重构先确认需要保持的行为。
- 检查工作区差异，识别已有修改；确定本次最小完整范围及对应验证方式。

### 实现中

- 规则变化修改权威实现，并让适用入口复用它；发现重复判定时，处理本次涉及的重复来源。
- 新增状态先判断是否可派生。必须保存的状态明确所有者和生命周期；新增缓存明确依赖、失效、清理与恢复方式。
- 跨模块修改明确输入、输出和副作用。回合推进由模拟层负责；渲染读取结果；相机交互不触发无关的数据修改。
- 新机制先完成最小可运行闭环；每个阶段都保留可运行状态。新增抽象须能指出实际消费者及减少的复杂度。
- 修复补充原失败场景的可重复验证；共享规则同时验证适用入口及失败后数据不变。

### 提交前

- 按改动检查放置与预览、运行与触发、显示与拾取、保存加载、撤销重做等受影响流程，不能仅验证新函数本身。
- 运行适当检查并查看实际结果。界面改动验证浏览器交互与截图；性能改动比较同一场景，明确测量范围。
- 检查暂存差异：实现、相关测试和文档属于同一个完整问题；无关修改和临时产物不得混入。
- 验证完成后及时提交。完成报告说明行为变化、验证结果及未解决的限制；仅在用户要求时推送。

审查发现重复业务规则、无法可靠失效的派生缓存、由动画推进回合、失败操作残留部分修改，或缺少对应验证时，应先修正再将该工作标记完成。与用户明确要求冲突时遵循用户要求，并说明实际影响。

## 开发工具使用要求

使用仓库已有工具落实上述流程。命令从仓库根目录运行；参数、检查范围和报告格式见 [开发检查说明](../docs/development-checks.md)。

| 时机或改动 | 必须执行的操作 |
| --- | --- |
| 修改后端规则或接口 | `npm --prefix work run check -- backend`，检查编译及后端回归结果。 |
| 修改前端、编辑器或渲染 | `npm --prefix work run check -- frontend`，检查共享后端编译、HTML 构建和前端回归结果。 |
| 修改开发工具 | `npm --prefix work run check -- tools`，验证工具自身的错误处理和报告行为。 |
| 完成代码修改、准备提交 | `npm --prefix work run check`，查看全部阶段；分组检查或单独的 `npm test` 不能替代完整检查。 |
| 验证界面或交互改动 | `npm --prefix work run browser:check`，查看截图，并补充本次受影响操作的实际浏览器验证。 |
| 打开修改后的效果 | `npm --prefix work run preview`，使用其输出的地址；源码变化后重新准备预览。仅验证 HTTP 就绪时使用 `npm --prefix work run preview -- --smoke`。 |
| 检查失败 | 先运行 `npm --prefix work run check:report`，定位首个失败阶段并阅读完整日志；根据报告重跑，修复后重新执行适用检查。 |

- 纯文档修改检查内容、链接及 `git diff --check`，无需执行无关构建。代码提交前的完整检查不得因“只是小改动”省略。
- 完整检查中止后，后续 `skipped` 阶段视为未验证。需要继续定位时单独运行相关分组，记录其范围；不能以局部通过宣称全部通过。
- 已有失败须记录失败测试、原因和报告路径，保留测试。区分已有问题和本次回归；未能确认原因时如实说明，不标记为已知无关失败。
- `.dev-checks/latest.json` 会被后续运行更新。引用重要失败或验证证据时保存具体 `report.json` 路径；`check:report` 读取成功不代表原检查通过。
- 构建、预览、完整检查、浏览器检查及成本实验不得在同一工作区并发运行。它们共享编译及 HTML 产物；运行后审查生成文件差异，不能覆盖已有修改。
- 浏览器烟测通过后仍须检查本次场景的显示、拾取和交互。截图像素非空、HTTP 就绪和单元测试通过不能代替视觉与行为验证。
- `frontend:fast -- 4` 仅用于完成构建后的快速反馈，不替代前端完整套件或提交检查。新增自动测试遵循既有发现规则；并行测试须隔离临时文件与外部副作用。
- 性能任务按需使用 `experiment:cost` 和对应场景测量，记录基线、相同操作及测量范围。没有整体开发耗时证据时，不把测试阶段提速宣称为整体效率提升。
- 完成报告列出实际执行的检查、通过或失败结果、未验证范围及必要的证据路径。提交前检查暂存差异，不提交 `.dev-checks/` 日志、截图、临时测量文件或无关生成产物。

## 原则的执行要求

以下要求用于新增功能、修复和重构的实现与审查。按改动范围提供对应证据，不要求为每次小改动另建文档。

### 1. 规则只有一个来源

- 实体叠加、terrain 承载、trigger 枚举及其互斥约束由所属领域模块统一定义。修改规则时先定位权威实现，不在界面、预览或渲染中补写另一份规则。
- 编辑器预览与正式放置复用同一放置判断；游戏运行复用适用的领域约束。放置、行走、传送和触发保留各自的操作入口，不强行合并为万能判断函数。
- 修改共享规则时，验证所有适用入口的结果一致，并覆盖拒绝操作时源数据不变。

### 2. 派生状态不重复保存

- 地形贴图、实体树显示、拾取数据和可选目标列表从权威实体数据及必要交互状态计算，不作为独立业务事实持久化。
- 选中实体 ID、工具模式等必要交互状态可以保存；其有效性须随实体删除、地图替换和模式变化重新检查。
- 缓存允许保留计算结果，但必须说明依赖及失效条件。修改或删除 terrain 后，关联贴图、显示和拾取应同时反映新状态。

### 3. 模拟与显示分离

- 动作与回合生命周期计算游戏状态，渲染及动画展示结果。动画时长、帧率和墙钟时间不能决定回合规则。
- 玩家相关状态机和交互逻辑必须位于 `player.cjs`，渲染模块不得重复推进回合或触发机制。
- 涉及回合机制的修改，验证空闲不推进、失败动作不误推进，以及调整动画速度不改变逻辑结果；撤销须恢复对应状态。

### 4. 模块边界按变化原因划分

- 相机模块处理视角，编辑命令处理数据修改，场景渲染处理展示；模块通过明确输入与通知协作。
- `app.js` 负责组合流程，可独立测试的业务判断和算法放入所属模块。
- 修改相机不能要求修改实体规则；修改渲染表现不能要求重写回合判断。跨边界改动须说明实际契约变化。

### 5. 先做最小可运行闭环

- 新方块或机制先完成“放置 → 运行 → 触发 → 显示 → 保存加载”，并验证相关撤销行为，再扩展配置选项。
- 最小闭环可以限制功能范围，但必须包含该范围内的必要校验与失败处理；未实现的选项不得作为可用能力展示。

### 6. 修 Bug 留下可重复验证

- 修复前记录最小地图或数据、失败操作及预期结果，先复现问题。
- 修复留下能验证原失败场景的回归测试；地图夹具使用合成数据，不依赖个人本地草稿。
- 数据规则使用自动测试；显示和拾取问题增加浏览器操作与截图验证。可重复的自动验证接入测试入口，人工验证记录步骤与结果。

### 7. 小步修改、及时提交

- 每次提交解决一个完整问题，包含相关实现、验证和文档；不为缩小提交而拆出不能工作的中间版本。
- 提交前检查暂存差异与对应验证结果，排除无关改动。遵循根目录的及时提交和按请求推送要求。

### 8. 用真实需要驱动抽象

- 提取公共机制前，指出现有重复、实际变化需求或明确的维护成本，以及抽象如何减少它们。
- 优先复用已有模块与接口；没有实际消费者或明确需求时，不预建通用引擎、插件框架和扩展层。
- 抽象应让调用者少理解内部细节；若增加配置和间接调用却没有减少复杂度，应简化设计。

## 职责与数据

- 每个模块应有明确职责与依赖边界。业务规则集中在其所属模块，界面、渲染和存储通过明确接口使用规则。
- 一个事实只维护一个权威数据来源。投影、索引与缓存属于派生数据，必须能从权威数据恢复，不能各自独立维护业务事实。
- 区分持久化配置、运行时状态、界面状态与调试状态，明确生命周期，避免互相污染。
- 依赖方向应清楚。纯数据与算法模块不依赖界面或外部副作用，便于独立验证。
- 接口明确输入、输出、错误和副作用；数据跨边界时验证结构及业务约束。
- 区域标签默认支持所有成功加载的实体 prefab（包括升降纸张及以后新增的实体）。资源目录读取时自动将实体 ID 合入区域标签的 BaseEntity，不要求新增实体时手工维护区域白名单；隐藏保护、区域唯一性和附着属性权限仍分别校验。

## 正确性与一致性

- 预览、正式操作、显示与保存使用一致的业务规则；复用规则实现，避免多份判定逐渐分歧。
- 操作应原子化：先准备和验证，再提交；失败不得留下部分修改。
- 数据改变时，同步处理受影响的派生数据和消费者，避免显示、拾取与实际状态不一致。
- 新增或修改数据须考虑序列化、导入导出、复制粘贴、撤销重做及运行时等适用流程。
- 优化不得绕过校验、丢弃有效操作或改变业务语义。边界条件、隐藏内容与异常路径也属于正确性要求。

## 性能与资源

- 先测量并定位主要成本，再优化。优先消除重复工作、无关计算和不必要的数据复制。
- 处理成本应尽量与实际变化范围匹配。高频路径避免无关的全量扫描、序列化、重建和外部写入。
- 可合并重复刷新与通知，但必须保留有效操作的顺序、结果和撤销语义。
- 缓存必须明确依赖、失效条件和生命周期；无法可靠失效时，不引入缓存。
- 资源必须明确所有权与释放时机，共享资源不能被单个使用者提前销毁。
- 异步任务必须处理取消、过期结果和执行顺序，避免旧任务覆盖新状态。
- 增量更新须覆盖完整依赖范围，并保留适用的恢复或全量重建路径。
- 诊断工具应按需开启，其自身开销不能成为常规运行成本。

## 复杂度与可维护性

- 优先使用已有模式和工具。只有能减少实际复杂度或解决明确问题时，才新增抽象、依赖和基础设施。
- 性能收益应足以抵偿额外维护成本；不得以猜测的未来需求引入复杂机制。
- 修改限制在必要范围内，不把无关重构混入功能修复。
- 命名表达领域含义；注释说明原因、约束和难以从代码看出的决定。
- 遇到需求歧义时，先检查现有代码和文档。普通实现选择自行处理；影响业务语义且无法推断的问题需要澄清。

## 验证与证据

- 验证规模与风险相匹配，覆盖真实行为和重要边界，不编写只重复实现细节的测试。
- 涉及共享规则或跨模块契约时，验证相关消费者；涉及界面显示或交互时，进行实际浏览器验证。
- 性能比较使用相同场景、操作和测量边界，预热后重复采样，说明环境、样本与统计方式。
- 结论只覆盖证据范围。局部算法基准不能证明整体交互性能，数据测试不能证明像素显示正确。
- 失败须定位并说明，区分已有问题与本次回归；不能删除无关测试或省略失败结果来宣称通过。
- 完成报告明确实际改动、已运行的验证与剩余限制，不报告未经验证的收益。

## 版本管理与文档

- 完成并验证的功能及时提交，以最小完整、可审查的工作单元拆分提交。
- 只暂存本次相关文件，保留用户已有修改；用户要求时才推送。
- 相关文档与实现放在同一提交中，规则或接口变化时同步更新说明。
- 按仓库要求更新受版本管理的生成产物，不提交密钥、依赖目录或临时诊断文件。
- 使用适合修改范围的检查。纯文档修改检查内容与差异即可，无需运行无关构建。
